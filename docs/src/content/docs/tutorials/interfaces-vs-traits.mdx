title: Interfaces vs Traits — When Each Is Right
description: "Compile-time vs runtime polymorphism in Sysl, with concrete examples of when each fits."
---

Sysl has two polymorphism mechanisms — **traits** (compile-time) and **interfaces** (runtime). Both let multiple types share a set of methods; they differ in how the dispatch happens. This tutorial walks through three real scenarios and shows which mechanism fits each.

## Quick comparison

| Aspect | Trait | Interface |
|--------|-------|-----------|
| Dispatch | Compile-time (monomorphized) | Runtime (vtable lookup) |
| Storage | None — calls are direct | 16-byte fat pointer per value |
| Declaration | Explicit `impl Trait[T]` required | Structural — none required |
| Generic methods | Yes | Yes (per-monomorphization vtable) |
| Type erasure | No (concrete type known) | Yes (forgotten after boxing) |
| Heterogeneous collections | No (different `T`s have different types) | Yes (all values share interface type) |
| Cost per call | Zero (direct call) | One indirect load + indirect call |

The choice usually comes down to: **do you need to put different concrete types into the same collection or pass them through the same parameter slot?** If yes, interface. If no, trait.

## Scenario 1: Sorting

The classic case. You have a list of items; you want to sort them. The compare function depends on the type:

### Trait approach

```sysl
trait Ord[T]
    cmp(a: T, b: T) -> int

impl Ord[int]
    cmp(a: int, b: int) -> int = a - b

impl Ord[string]
    cmp(a: string, b: string) -> int
        if a < b then -1
        elif a > b then 1
        else 0

sort_inplace[T: Ord](a: &[]T)
    // ... compare with Ord.cmp(a[i], a[j]) ...
```

`sort_inplace` is generic. The compiler generates one specialized version per concrete `T`:

- `sort_inplace_i32` for `&[]int`
- `sort_inplace_string` for `&[]string`

Each version makes direct calls to `Ord_cmp_i32` or `Ord_cmp_string`. No vtable, no indirect calls.

**Why a trait fits:** at every call site, the compiler knows the concrete `T`. There's no need to defer the dispatch to runtime — you'd be paying for flexibility you don't use.

### Why an interface would be wrong

```sysl
interface Comparable
    cmp(other: Comparable) -> int

sort_inplace_comparable(a: &[]Comparable)
    // ... compare with a[i].cmp(a[j]) ...
```

Could you write this? Yes. Should you? No:

- **Every element is boxed.** A `Comparable` is a 16-byte fat pointer; an `int` is 4 bytes. You've quadrupled storage to gain... nothing.
- **Every call is indirect.** vs the direct call generated by `Ord.cmp`.
- **The `cmp` argument signature is awkward.** Comparing `Comparable` to `Comparable` doesn't statically constrain "both sides are the same type" — you might accidentally `cmp` an `int` with a `string` and get nonsense.

## Scenario 2: A GUI scene graph

Now the inverse: you have a collection of objects that share a behavior but are of different types. The compiler can't know at each call site which kind it's dealing with.

### Interface approach

```sysl
interface Drawable
    draw() -> unit
    bounds() -> Rect

struct Circle
    center: Point
    radius: int

Circle.draw() -> unit = ...
Circle.bounds() -> Rect = ...

struct Text
    str: string
    pos: Point

Text.draw() -> unit = ...
Text.bounds() -> Rect = ...

render_scene(items: []Drawable)
    for it in items
        it.draw()
```

`items` is a heterogeneous slice — some elements are `Circle`, some are `Text`, the iteration treats them uniformly. The vtable dispatch picks the right `draw` for each.

**Why an interface fits:**

- **Heterogeneous collection.** You can't express "slice of mixed `Circle` and `Text`" with a trait.
- **Structural satisfaction.** Adding a new shape `Image` just requires defining `Image.draw()` and `Image.bounds()` — no `impl Drawable for Image` block.
- **Runtime is the right time.** The scene graph is built dynamically; you don't know what types it contains until the program runs.

### Why a trait would be wrong

You'd have to encode the type at the slice level:

```sysl
enum SceneItem
    SCircle(Circle)
    SText(Text)

trait Drawable[T]
    draw(t: T) -> unit
```

This is the same approach Rust took *before* trait objects (`dyn Trait`). It works, but:

- Adding a new shape requires editing the `SceneItem` enum **and** writing a new `impl`. With interfaces, you just write the struct's methods.
- The match-and-dispatch pattern (`item match { SCircle(c) -> Drawable.draw(c); SText(t) -> Drawable.draw(t); }`) is exactly the vtable lookup, but spelled out by hand.

The interface mechanism *is* this pattern, automated.

## Scenario 3: Hashing

A `Hash` trait is the standard textbook example:

```sysl
trait Hash[T]
    hash(x: T) -> u64

impl Hash[int]
    hash(x: int) -> u64 = u64(x) * 0x9E3779B97F4A7C15u64

impl Hash[string]
    hash(s: string) -> u64
        var h = 0xCBF29CE484222325u64
        for c in s
            h = h ^ u64(c)
            h = h * 0x100000001B3u64
        h

struct HashMap[K: Hash + Eq, V]
    // ...

main() -> int
    var m: HashMap[string, int] = HashMap.empty()
    m.insert("hello", 42)
    m.get("hello") match
        Some(v) -> v
        None -> -1
```

**Why a trait fits:** every concrete `HashMap[K, V]` knows its `K` at compile time. The compiler specializes the hash function into the lookup code; no indirection.

### Why an interface would be wrong here

You'd lose the ability to constrain `K` and `V` independently. `HashMap[Hashable, int]` would let you mix string keys, int keys, and custom-type keys *in the same map*. That sounds powerful but it's almost never what you want:

- All keys must be the same concrete type for `eq` to make sense (you can't compare "string `hello`" to "int 42" sensibly).
- Hashing strings differently from ints differently from custom types is the whole point of `Hash` being polymorphic.

The trait approach keeps these constraints in the type system. The interface approach throws them away.

## A useful heuristic: how the type is decided

- **Type is known at the call site** → trait.
- **Type is decided at runtime (input data, user choice, plugin system)** → interface.
- **Type might be either** → start with a trait. Adding interface boxing later is cheap; removing trait dispatch is hard.

## A combined design

Often the right design uses both. A library defines a *trait* for compile-time-known cases and a parallel *interface* for plug-in extensibility:

```sysl
// Compile-time path
trait Codec[T]
    encode(v: T, w: &Writer)
    decode(r: &Reader) -> T

// Runtime path
interface AnyCodec
    encode_dyn(v: *u8, w: &Writer)
    decode_dyn(r: &Reader) -> *u8

// Adapter from trait to interface
struct CodecBox[T: Codec]
    // ...

CodecBox.encode_dyn(...) -> unit = ...
```

Users who know the concrete type at compile time get the fast path (trait). Users who need plugin-style dispatch get the flexible path (interface). The trait body provides the implementation for both.

## The interface "owns" flag

One subtlety unique to interfaces: when you box a struct into an interface value, the data pointer may either:

- **Share storage with the source** — used when the box is consumed within the source's lifetime (passed to a function parameter, indexed into).
- **Own an independent heap copy** — used when the box escapes (return value, stored in `Option[Iface]`, captured by escaping closure).

The compiler picks automatically. You don't write `owns: true/false` anywhere. The implication: **interface values are always safe to use, even after the source has gone out of scope**, when they came from a return / `Option` / `Result` / heap-stored field.

See [Interfaces: Boxing and the `owns` flag](/language/functions/interfaces#boxing-and-the-owns-flag) for full details.

## What you've learned

- **Traits** for compile-time polymorphism — generic functions, operator overloading, hash maps, sort routines.
- **Interfaces** for runtime polymorphism — heterogeneous collections, plug-in architectures, dependency injection.
- **The choice usually hinges on heterogeneity**: same concrete type per call site → trait; mixed types in the same slot → interface.
- **You can use both** in the same library, with the interface delegating to the trait's implementation.
